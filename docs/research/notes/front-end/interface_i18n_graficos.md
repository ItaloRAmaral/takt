## 1. Componentes: Radix + shadcn/ui vs React Aria Components vs Base UI vs MUI vs Mantine vs Ark UI

### Takeaway
Em outubro de 2026, o caminho padrão do ecossistema shadcn/ui passou a ser **Base UI** (default desde julho de 2026). **React Aria** virou uma terceira "base" oficial do shadcn, e Radix segue suportado, mas não é mais a recomendação para projetos novos. Para o Takt, que precisa de tooltip e toggletip que cumpram a WCAG 1.4.13 e funcionem no toque, **Base UI** (Tooltip + Popover `openOnHover` para infotips) ou **React Aria Components** (Tooltip + Popover/Dialog) estilizados com Tailwind v4 via shadcn são as opções mais defensáveis. Nenhuma biblioteca abre tooltip no toque: o toggletip tem de ser um Popover acionado por botão.

**Acessibilidade de tooltip e toggletip (o requisito central do Takt)**
- WAI-ARIA APG, Tooltip Pattern: "This design pattern is work in progress; it does not yet have task force consensus." O padrão define `role="tooltip"`, `aria-describedby` no gatilho, Escape fecha e "Focus stays on the triggering element". Além disso: "Tooltip widgets do not receive focus. A hover that contains focusable elements can be made using a non-modal dialog." — [W3C WAI-ARIA APG: Tooltip](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/)
- Atas do grupo APG de 2021 (com Sarah Higley) consideraram "show on touch start, hide on touch end" para toque. Para conteúdo maior que um rótulo, a recomendação foi usar toggletip/dialog e evitar auto-dismiss. **São atas, não norma.** — [W3C APG minutes 2021-08-24](https://www.w3.org/2021/08/24-aria-apg-minutes.html); [w3c/aria-practices PR #811](https://github.com/w3c/aria-practices/pull/811)
- **Base UI Tooltip**: "tooltips are disabled on touch devices". `disableHoverablePopup` vem em `false` por padrão, então o popup é hoverable (requisito da 1.4.13). Escape fecha (`escape-key`). "Tooltips are visual-only elements and are not a replacement for labeling the trigger": o gatilho precisa de `aria-label`. Para infotips (ícone "i"), a doc diz para usar **Popover com `openOnHover`**, para que "touch users and screen reader users can access the content". Regra prática da doc: se o propósito do gatilho é abrir o popup, use popover; senão, tooltip. — [Base UI: Tooltip](https://base-ui.com/react/components/tooltip)
- **React Aria Tooltip**: abre no hover depois de um warmup e "instantly on focus". Quando um tooltip já está aberto, os vizinhos abrem na hora. "Tooltips are not shown on touch screen interactions." A doc recomenda "Ensure that your UI is usable without tooltips" e indica Popover/PreviewTrigger para informação que precisa persistir. O índice de componentes lista Dialog, Popover e Tooltip em Overlays, **sem componente Toggletip**. — [React Aria: Tooltip](https://react-aria.adobe.com/Tooltip); [React Aria Components index](https://react-spectrum.adobe.com/react-aria/components.html)
- **Radix Tooltip**: "Closes when the trigger is activated or when pressing escape". `delayDuration` padrão é 700 ms e `skipDelayDuration` 300 ms. Existe a prop `disableHoverableContent`, mas a página não explica o default. A doc **não fala de comportamento em toque**. — [Radix Primitives: Tooltip](https://www.radix-ui.com/primitives/docs/components/tooltip)
- **Ark UI Tooltip**: afirma cumprir o "Tooltip WAI-ARIA design pattern". `closeOnEscape` vem `true`, mas **`interactive` vem `false` por padrão**, ou seja, o conteúdo não é hoverable sem configuração explícita. A doc não fala de toque. Há um componente Hover Card separado. — [Ark UI: Tooltip](https://ark-ui.com/docs/components/tooltip)

**Estilização e tema**
- O Mantine recomenda CSS Modules ("the most performant and flexible way") e expõe o tema como CSS variables (`var(--mantine-color-red-5)`), com `light-dark()` para dark mode. A página de estilos não menciona Tailwind. — [Mantine: Styles overview](https://mantine.dev/styles/styles-overview/)
- O Ark UI expõe estado via data attributes (`data-state`, `data-side`) e CSS variables, e oferece `asChild`. Esse modelo de estilização headless combina com Tailwind. — [Ark UI: Tooltip](https://ark-ui.com/docs/components/tooltip)

### Inferences
- [Estimativa] **Nenhuma das libs resolve sozinha o toggletip em toque.** Base UI e React Aria desligam tooltip no toque de propósito, e Radix e Ark não documentam o caso. Para o Takt: (a) usar **Tooltip** só como rótulo suplementar de botões de ícone, com o mesmo texto em `aria-label`; (b) implementar **toggletip** como Popover não modal aberto por um botão ("i" ou "?"), com `aria-expanded`, Escape, foco que volta ao gatilho e conteúdo **sem elementos interativos** (requisito do PDR). Se precisar de link "saiba mais", ele deve abrir o painel lateral, e o link fica no painel, não no toggletip. No Base UI isso é literalmente o padrão documentado (`Popover` + `openOnHover`).
- [Estimativa] Base UI e React Aria ganham de Radix na **robustez de longo prazo**: a Base UI tem time full time da MUI e cadência quase mensal (1.0 em dez/2025, 1.9 em out/2026), e a React Aria tem a Adobe e releases frequentes. O Radix voltou a publicar (1.8.1 em out/2026), mas o próprio shadcn recomenda Base UI para projetos novos.
- [Estimativa] **Base UI via shadcn (Tailwind v4)** é o caminho de menor atrito para o Takt: é o default atual do shadcn, tem a maior massa de exemplos/blocks e cobre tooltip, popover, dialog e drawer. **React Aria via shadcn (`--base aria`)** é a alternativa para quem prioriza a qualidade de a11y testada em leitores de tela (internacionalização de componentes, i18n de datas/números em DatePicker/NumberField). O custo é o pacote maior (a medida do bundlephobia é do pacote inteiro, o que importa é o tree-shaken) e uma base shadcn mais nova (jul/2026).
- [Conhecimento prévio, não reverificado nesta sessão] A React Aria tem `NumberField` e `DatePicker` com formatação locale-aware via `@internationalized/number` e `@internationalized/date`, útil para entrada de parâmetros em pt-BR (vírgula decimal). Também tem componentes Drawer/Modal com focus trap e um plugin Tailwind (`tailwindcss-react-aria-components`) para estados como `data-[hovered]`. Conferir em react-aria.adobe.com.
- [Conhecimento prévio, não reverificado] O MUI v9 continua com Emotion/`sx` como modelo principal de estilização, o que **briga com Tailwind v4** (é possível combinar, mas é atrito). O Mantine usa CSS Modules e também não é Tailwind-first. As duas libs trazem design system opinativo (Material ou Mantine), menos adequado a um visual próprio do Takt.
- [Palpite] O painel lateral não modal de explicações não deve ser um `Dialog` modal nem um Drawer modal. Deve ser uma região (`<aside>` com `aria-labelledby`) ou um Dialog com `modal={false}`, sem focus trap, para coexistir com o editor 3D. Base UI (`Dialog` com `modal={false}`) e React Aria (`Modal` é sempre modal; para não modal usar `Popover` com `isNonModal` ou uma região simples) se comportam de forma diferente aqui, e vale prototipar.
- [Palpite] O Ark UI (Zag.js, multi-framework) é tecnicamente sólido, mas tem adoção ~20x menor que Base UI/Radix e não é uma base do shadcn, o que o torna uma escolha de nicho para o Takt.

### Gaps
- Não encontrei **declaração primária** (tweet, post da WorkOS, issue do Radix) sobre o roadmap ou a manutenção do Radix. As alegações de 2025 vêm de post secundário.
- Não encontrei auditoria independente recente (2025-2026) de especialistas em a11y (ex.: Adrian Roselli, Sarah Higley, Deque) comparando Base UI vs React Aria vs Radix. Um teste próprio com NVDA/JAWS/VoiceOver/TalkBack fica recomendado.

## 2. i18n: next-intl vs react-i18next/i18next vs Lingui vs FormatJS (react-intl)

### Takeaway
As quatro estão ativamente mantidas em out/2026 (todas com release nas últimas 3 semanas). **next-intl** é a escolha natural se o Takt for Next.js App Router: ICU nativo, tipos estritos de chaves e argumentos ICU, RSC, e `use-intl` para Vite. **Lingui 6** é a mais leve (core ~2 KB gzip) e tem a melhor extração. **react-i18next** domina em adoção, mas ICU é plugin opcional. **react-intl** é a referência ICU/FormatJS. A formatação pt-BR (vírgula decimal, datas) vem do próprio `Intl` em todas.

**next-intl**
- A v4.0 (12/03/2025) trouxe "revamped augmented types", locales estritamente tipados e **"strictly typed ICU arguments"**. Messages e Formats são registrados numa interface `AppConfig` (ex.: `Messages: typeof en`), e `useLocale()`/`<Link />` passam a usar a union de locales do app. — [next-intl 4.0 blog](https://next-intl.dev/blog/next-intl-4-0)
- Os READMEs das versões 4.12 a 4.14 listam a sintaxe ICU e chaves type-safe em tempo de compilação como features centrais. — [next-intl 4.14.2 README (jsDelivr)](https://cdn.jsdelivr.net/npm/next-intl@4.14.2/README.md)
- A v4.5.0 (2025-11-07) adicionou **`useExtracted` (experimental)**: mensagens inline no código ganham chave gerada automaticamente, o arquivo do locale fonte recebe o texto e os locales alvo recebem entradas vazias. A extração roda em `next dev`/`next build` via loader Turbopack/Webpack e precisa ser habilitada no plugin. Há suporte a `.po`. A doc diz que foi feito também para agentes de IA. — [GitHub release v4.5.0](https://github.com/amannn/next-intl/releases/tag/v4.5.0); [next-intl docs: extraction](https://next-intl.dev/docs/usage/extraction); [next-intl docs: agents](https://next-intl.dev/docs/workflows/agents); [newreleases 4.5.6](https://newreleases.io/project/npm/next-intl/release/4.5.6)
- O core `use-intl` é "agnostic and can be used independently—either in React apps or any other JavaScript environment". Ele oferece `useTranslations`, `useFormatter` (números, datas, listas) e `IntlProvider`, mas não tem routing nem integração com RSC/Server Actions. `use-intl/core` tem `createTranslator` e `createFormatter`, que recebem toda a configuração explicitamente, o que serve para um app Vite ou para formatar fora do React. — [next-intl docs: core library](https://next-intl.dev/docs/environments/core-library)

**i18next / react-i18next**
- Os tipos funcionam por augmentation de `CustomTypeOptions`, com `resources` como "the most important option" para inferir chaves e tipos de retorno. A validação legada "enumerate[s] every possible key, which gets expensive with thousands of keys" e pode dar OOM com typescript-eslint. A saída recomendada é a **selector API** (`enableSelector: "optimize"`), capaz de "arbitrarily large translation sets". O modo `"strict"` (v26.1.0+) exige namespace explícito. A doc avisa que o suporte de tipos à API por string **pode ser deprecado na v27**. Requer TS 5. — [i18next docs: TypeScript](https://www.i18next.com/overview/typescript)
- Breaking changes da v26.0.0: remoção de `initImmediate` (use `initAsync`) e de `interpolation.format` legado (agora sempre se usa o Formatter embutido, baseado em `Intl`, ou um customizado via `services.formatter.add()`), além da remoção do aviso de suporte no console. A v26.3.0 adicionou o tipo `ResourceNamespaceMap`. — [newreleases: i18next 26.0.0](https://newreleases.io/project/npm/i18next/release/26.0.0)

**Lingui**
- A v6.0.0 (2026-04-22) é **ESM-only**, reduz o grafo de dependências, remove APIs deprecadas e melhora o TypeScript. Remove o pacote `@lingui/macro`, o extrator TypeScript antigo e o CRA. Exige Node ≥ 22.19 e passa a gerar IDs em Base64 urlsafe. Os pré-releases trouxeram compatibilidade com o **Vite 8** no `@lingui/vite-plugin` e um fix de identidade do contexto i18n para **React Compiler**. — [GitHub release v6.0.0](https://github.com/lingui/js-lingui/releases/tag/v6.0.0); [v6.0.0-next.0 / next.2 / next.3 (GitHub releases)](https://github.com/lingui/js-lingui/releases); [Lingui 6.0 blog](https://lingui.dev/blog/2026/04/22/announcing-lingui-6.0); [migration guide 6.x](https://lingui.dev/releases/migration-6)

**FormatJS / react-intl**
- A v12.0.0 (2026-09-15) tem como breaking change "simplify typed helper calls and generated contracts" em `@formatjs/intl` 6.0.0, ou seja, mexe justamente na camada de tipos e contratos gerados. — [GitHub release react-intl@12.0.0](https://github.com/formatjs/formatjs/releases/tag/react-intl%4012.0.0)

**Intl nativo em pt-BR (verificado empiricamente, Node 20.10 / ICU embutido)**
- `new Intl.NumberFormat('pt-BR').format(1234567.891)` → `1.234.567,891`, enquanto em `en` dá `1,234,567.891`. Percentual em pt-BR: `87,3%`. Data com `dateStyle:'medium', timeStyle:'short'` → `20 de out. de 2026, 11:05`. — teste local com `node -e` em 2026-10-20 (reprodutível; ver [MDN Intl.NumberFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat))
- `Intl.PluralRules('pt-BR')` tem as categorias `one`, `many` e `other`, e **`select(0)` retorna `"one"`** (o 0 é singular em pt-BR, segundo o CLDR). Em `pt-PT` e `en`, 0 retorna `"other"`. — mesmo teste local; ver [MDN Intl.PluralRules](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules)

### Inferences
- [Estimativa] **Next.js App Router → next-intl**: tem ICU nativo (plural/select/number/date dentro da mensagem), tipos estritos de chave **e** de argumentos ICU via `AppConfig`, formatação em Server Components e `useExtracted` para quem não quer manter chaves à mão (é experimental, então convém evitar em produção até estabilizar). **Vite puro → `use-intl`** (mesma API, sem routing) ou Lingui.
- [Estimativa] **Lingui 6** é a melhor opção se a prioridade for bundle mínimo e extração de catálogo (macros `t`/`<Trans>` com PO/JSON e compile step). Por ser ESM-only e exigir Node 22.19+, combina com um stack novo (Vite 8, React Compiler). O custo é depender de macro (SWC/Babel plugin) na toolchain, o que no Next.js exige plugin SWC.
- [Estimativa] **react-i18next** tem o maior ecossistema (backends, detecção de idioma, ferramentas de tradução), mas o formato padrão é o JSON próprio do i18next com sufixos de plural (`_one`, `_other`, `_many`). **ICU exige o plugin `i18next-icu`** [conhecimento prévio, não reverificado]. Os tipos estão migrando para a selector API, o que é uma mudança em curso (v25.4 → v26 → v27).
- [Estimativa] Sobre o **pt-BR `0 → one`**: mensagens do tipo "{count, plural, one {# peça} other {# peças}}" vão renderizar "0 peça" em pt-BR. Se o desejado for "nenhuma peça", é preciso o caso exato `=0 {...}` no ICU. Vale como regra no guia de estilo de mensagens do Takt. A categoria `many` em pt aparece para números compactos e grandes (ex.: "1 milhão") no CLDR recente [Palpite sobre o motivo; o fato verificado é só a presença da categoria].
- [Estimativa] **Erros vindos do servidor**: o padrão comum nas quatro libs é o backend devolver um `code` estável (ex.: `MODEL_CYCLE_DETECTED`) mais parâmetros, e o front mapear `code` → chave de mensagem (`t(\`errors.${code}\`, params)`), com fallback genérico para códigos desconhecidos. Com next-intl ou i18next tipados, isso pede uma union TypeScript dos códigos gerada a partir do contrato da API (OpenAPI) para que o mapeamento seja verificado em compilação. Chaves dinâmicas quebram a extração automática (Lingui/`useExtracted`), então essas mensagens precisam ser declaradas explicitamente (ex.: `defineMessages`/catálogo manual).
- [Estimativa] Números e datas: as quatro libs delegam a `Intl.NumberFormat`/`Intl.DateTimeFormat`, então a vírgula decimal em pt-BR sai "de graça" quando a formatação passa pelo formatter da lib (`format.number`, `{n, number}`, `i18n.number`). O risco real está em **gráficos e inputs**: as libs de gráfico formatam ticks e tooltips por conta própria, e é preciso injetar o formatter do locale (ver seção 3). Para inputs numéricos, `Intl` não faz parse, por isso NumberField do React Aria ou parser próprio.
- [Conhecimento prévio, não reverificado] O FormatJS oferece `@formatjs/cli extract`/`compile` e plugins SWC/Babel para gerar IDs e pré-compilar mensagens ICU (dispensando o parser em runtime). A tipagem de IDs se faz via namespace global `FormatjsIntl.Message`.

## 3. Gráficos: Recharts vs ECharts vs visx vs uPlot vs Observable Plot vs Nivo vs Chart.js

### Takeaway
Para séries temporais com milhares de pontos × várias séries, marcador vertical de warm-up e bandas de IC, as opções em **canvas** (ECharts 6, uPlot, Chart.js) são as seguras em desempenho. **ECharts** é a mais completa, com `markLine`/`markArea`, dataZoom, sampling LTTB, módulo `aria` com descrição automática e decals, e manutenção ativa. A **Recharts 3** (SVG) é a mais adotada e a mais simples para cards de KPI e gráficos pequenos, e é acessível por teclado por padrão, mas exige downsampling. **uPlot** é imbatível em velocidade e tamanho, mas sem a11y nem wrapper oficial, e sem release desde mar/2025. Nenhuma lib substitui uma **tabela de dados alternativa**, que o Takt deve oferecer por conta própria.

### Inferences
- [Conhecimento prévio, não reverificado] **Annotations em cada lib**:
  - ECharts: `markLine` com `xAxis: <t_warmup>` para a linha vertical de warm-up e `markArea` para sombrear o período de warm-up. A banda de IC sai com duas séries `line` empilhadas (`stack`, a inferior transparente e a superior com `areaStyle`, como no exemplo oficial "Confidence Band") ou com `custom` series. Tem `dataZoom` (inside/slider), `sampling: 'lttb'` em séries line e `tooltip.trigger: 'axis'`.
  - Recharts: `<ReferenceLine x=…/>`, `<ReferenceArea x1 x2/>` e `<Area dataKey={d => [lo, hi]}/>` para range/banda de IC. Zoom não é nativo (se faz com Brush ou estado de domínio).
  - Chart.js: `chartjs-plugin-annotation` (linhas e caixas), `fill` entre datasets para a banda, plugin `decimation` (LTTB/min-max) embutido e `chartjs-plugin-zoom`. Os plugins não têm release desde o fim de 2024.
  - uPlot: `bands` nativo, linha vertical via hook `draw`.
  - Observable Plot: `ruleX`, `areaY` (y1/y2) e `tip`, em SVG, sem zoom nativo e sem componente React (integração via `useEffect` + `ref`).
  - Nivo: `markers` em `@nivo/line` e variante `LineCanvas`, mas sem release desde mai/2025.
- [Estimativa] **Volume do Takt** (milhares de pontos × várias séries, ex.: 5 séries × 5.000 pontos = 25 mil pontos): canvas (ECharts/uPlot/Chart.js) aguenta folgado. Em SVG (Recharts/visx/Plot/Nivo SVG), cada ponto vira nó DOM, então seria preciso **downsampling no servidor ou no cliente** (LTTB para ~1–2 mil pontos por série visível) e re-amostragem no zoom. O downsampling é boa prática de qualquer forma, porque o servidor de simulação pode devolver séries já agregadas por janela.
- [Estimativa] **Recomendação técnica**: **ECharts 6** para os gráficos de séries temporais (performance em canvas, `markLine`/`markArea`, dataZoom, sampling, `aria` com descrição e decals, `locale`/`formatter` customizáveis, manutenção Apache ativa), integrado por wrapper fino próprio (`useEffect` + `echarts.init` + `setOption`, ~50 linhas) ou `echarts-for-react`, com build modular para reduzir o bundle. **Recharts 3** (ou componentes próprios em HTML/CSS) para sparklines e cards de KPI, onde o volume é pequeno e o `accessibilityLayer` padrão ajuda. A alternativa minimalista é **uPlot**, se o bundle e o FPS forem críticos, ao custo de construir a11y, tooltip e legenda à mão e de um projeto de um mantenedor só, sem release há 19 meses.
- [Estimativa] **Acessibilidade de gráficos**: nenhuma lib oferece tudo o que o Takt precisa. Canvas é opaco a leitores de tela, e o ECharts mitiga isso só com `aria-label` descritivo. O padrão recomendável é: (1) título e resumo textual gerado pelo app ("Throughput médio após warm-up: 12,4 peças/h, IC 95% [11,9; 12,9]"); (2) **tabela de dados alternativa** (toggle "ver como tabela", com dados agregados e formatados no locale); (3) marcador de warm-up anunciado no texto; (4) cores mais padrão ou decal para distinguir séries. A navegação por setas da Recharts é um bônus, mas não substitui a tabela.
- [Estimativa] **Locale nos gráficos**: todas formatam ticks e tooltips por callback. É preciso passar `Intl.NumberFormat(locale)` e `Intl.DateTimeFormat(locale)` vindos da camada de i18n (ex.: `axisLabel.formatter` no ECharts, `tickFormatter` na Recharts, `values` nos eixos do uPlot). Sem isso, aparece ponto decimal em pt-BR. O ECharts também tem `echarts.registerLocale` para textos internos (toolbox/dataZoom) [conhecimento prévio].
- [Palpite] Observable Plot é excelente para gráficos exploratórios estáticos, mas é 0.x, sem release desde fev/2025, SVG e sem integração React oficial. Não é a melhor aposta para gráficos interativos centrais do produto.
