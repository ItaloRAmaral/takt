## 1. Maturidade, manutenção e governança

### Takeaway
As quatro opções estão ativamente mantidas em out/2026. Em adoção, three.js e o ecossistema pmndrs (R3F, drei, Zustand) ficam uma ou duas ordens de grandeza acima de Babylon e PlayCanvas, e o R3F é a única camada React madura entre elas. Babylon tem a governança mais "corporativa" (Microsoft) e a cadência mais previsível, com minor semanal. O R3F está em transição para a v10 (WebGPU-first, ainda alpha), e a linha estável recomendada continua sendo a v9.x.

## 2. Performance para centenas a milhares de objetos

### Takeaway
Para o Takt, que tem de dezenas a alguns milhares de objetos low-poly com poucos tipos de geometria, o gargalo é **draw calls e CPU por frame**, não GPU. Todas as engines resolvem isso com instancing: InstancedMesh/BatchedMesh no three.js e thin instances no Babylon. No R3F, a regra é mutar via refs dentro de `useFrame` e nunca passar estado por frame pelo React.

### Cited Findings
- A doc do R3F diz que cada mesh é um draw call e recomenda mantê-los baixos, com **"hard maximum of 1000 and ideally a few hundred or fewer"**. Para muitos objetos repetidos, recomenda `instancedMesh` (um draw call). — [R3F: Scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)
- O R3F tem `frameloop="demand"`: renderiza só quando props mudam. Mutações fora do React exigem `invalidate()`, e múltiplas chamadas não causam múltiplos renders. A doc também oferece `PerformanceMonitor` (drei) e `regress()` para baixar a qualidade durante interação. — [R3F: Scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)
- **Pitfalls oficiais do R3F**:
  - "You might be tempted to setState inside `useFrame` but there is no reason to."
  - Updates rápidos devem ser mutações em refs: "`useFrame` is your per-component render-loop".
  - Use deltas para ficar independente do refresh rate.
  - Para estado transitório com Zustand, leia `api.getState()` dentro do `useFrame`: "Using state-managers and selective state is fine, but not for updates that happen rapidly."
  - Evite criar objetos (`new Vector3`) por frame e reutilize-os para não acionar o GC.
  - Prefira alternar `visible` a montar e desmontar.
  - — [R3F: Performance pitfalls](https://r3f.docs.pmnd.rs/advanced/pitfalls)
- **BatchedMesh (three.js)**:
  - É "A special version of a mesh with multi draw batch rendering support". Renderiza muitos objetos com **geometrias diferentes e o mesmo material** em um draw call.
  - API por instância: `addGeometry`/`addInstance`, `setMatrixAt`, `setColorAt`, `setVisibleAt`, `setGeometryIdAt`, `deleteInstance`, `optimize()`.
  - Tem `perObjectFrustumCulled` (default true) e `sortObjects`.
  - Matrizes com escala negativa não são suportadas.
  - — [three.js docs: BatchedMesh](https://threejs.org/docs/pages/BatchedMesh.html)
- **Mudanças recentes de instancing no three.js**:
  - r184 removeu caminhos de instancing depreciados e adicionou no WebGPURenderer um fallback de WEBGL_multi_draw.
  - r185: "Fully support `InstancedMesh` with render bundles".
  - r186: correções de BatchedMesh (visibilidade em `setGeometryIdAt`, draw offsets no WebGPU).
  - — [three.js releases](https://github.com/mrdoob/three.js/releases)
- **drei `<Instances>`/`<Instance>`**:
  - É um wrapper declarativo de `THREE.InstancedMesh` ("hundreds of thousands of objects in a single draw call, but declaratively!"), com props `limit` e `range` e eventos e cor por `<Instance>`.
  - A doc avisa que "it comes at the cost of CPU overhead" e recomenda `InstancedMesh` cru para contagens muito grandes.
  - — [drei: Instances](https://drei.docs.pmnd.rs/performances/instances)
- **Babylon thin instances**:
  - Existem desde a v4.2. Cada instância é só uma matriz, sem objeto por instância, o que torna "thousands" viáveis.
  - Visibilidade é tudo ou nada ("all thin instances are drawn... or none are").
  - Adicionar ou remover é mais caro que com instances normais. Funcionam melhor para muitos objetos estáticos.
  - Para updates por frame: buffer atualizável (`thinInstanceSetBuffer(..., false)`) + `thinInstanceBufferUpdated`. Atributos por instância (ex.: cor) via `thinInstanceRegisterAttribute`.
  - Suportam picking e sombras.
  - — [Babylon docs: Thin Instances](https://doc.babylonjs.com/features/featuresDeepDive/mesh/copies/thinInstances)

### Inferences
- **[estimativa]** O orçamento do Takt é confortável. Com algo como 10 a 30 tipos de máquina, esteira, buffer e peça, cada tipo vira um InstancedMesh (ou tudo vai para alguns BatchedMesh por material). Com flat shading e cor por instância (`setColorAt`), milhares de objetos cabem em **dezenas de draw calls**, bem abaixo do teto de algumas centenas da doc do R3F.
- **[estimativa]** Replay a 1x–100x: a velocidade não muda o custo por frame. A 100x, mais eventos são consumidos por frame, mas cada frame continua sendo um único `update` de N matrizes e cores. O padrão recomendado:
  1. O relógio da simulação fica num ref ou num store Zustand não reativo.
  2. Dentro de `useFrame`, calcular o tempo simulado (`t += delta * speed`).
  3. Aplicar os eventos com `t_evento <= t` a partir de um cursor ordenado.
  4. Interpolar posições de peças entre eventos.
  5. Escrever em `instanceMatrix`/`instanceColor` e marcar `needsUpdate`.
  - Isso segue diretamente os pitfalls oficiais.
- **[estimativa]** O "seek" (pular para o instante X a 100x) exige conseguir reconstruir o estado em T sem reaplicar o log inteiro (snapshots/checkpoints). Esse é um problema de domínio, independente da engine.
- **[estimativa]** Para elementos editáveis (máquinas que o usuário arrasta), `<mesh>` individuais funcionam até centenas. Acima disso, use `<Instances>` da drei (a ergonomia compensa o overhead de CPU na faixa de milhares) ou InstancedMesh cru para peças em movimento.
- **[palpite]** Peças em movimento são o único conjunto que pode chegar a milhares de objetos atualizados por frame. Devem ir sempre para InstancedMesh cru, nunca para `<Instance>` declarativo.

### Gaps
- Não encontrei benchmark atual e neutro comparando three.js e Babylon para milhares de instâncias dinâmicas. Os ganhos de "2–10x" ou "10–100x" do WebGPU em blogs não são verificáveis.
- A doc de thin instances não fala de update parcial de buffer nem traz números de benchmark.

## 3. WebGPU em 2026 e fallback WebGL2

### Takeaway
WebGPU está habilitado por padrão em Chrome/Edge (desktop e Android 12+) e Safari 26. No Firefox, só em Windows e macOS. Firefox Linux e Android, e Chromium Linux fora de hardware específico, ainda não têm. Por isso o fallback **WebGL2 continua obrigatório**. O three.js `WebGPURenderer` e o R3F v10 fazem fallback automático para WebGL2. O Babylon exige escolher o engine (WebGL ou WebGPU) antes de criar a cena. Para o Takt (low-poly, sem compute pesado), WebGPU não traz vantagem decisiva hoje.

### Cited Findings
- **gpuweb Implementation Status** (página editada em **2026-10-02**):

  | Browser | Suporte por padrão | Ainda não suportado |
  |---|---|---|
  | Chromium | Mac, Windows x64/x86 e ChromeOS desde 113. Android 12+ (ARM/Qualcomm/Intel) desde 121. Linux Intel Gen12+ desde 144 e NVIDIA (driver 535.183.01+) sob Wayland desde 147 | Outros Linux só via flag. Windows ARM64 via flag |
  | Firefox | Windows desde 141. Mac Apple Silicon desde 145 (macOS 26+) e desde 147 em todos os macOS | Linux só no Nightly ("expects to ship in 2026"). Android atrás de flag |
  | Safari | macOS, iOS/iPadOS e visionOS 26, "enabled by default" | — |

  — [gpuweb wiki: Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- O caniuse (dados de uso de set/2026) mostra 85,8% de suporte global + 2,02% parcial = 87,82%. Marca Safari desktop 26.x/27 como "parcial" e o **Firefox como "disabled by default" até a 161**, o que **conflita** com a página do gpuweb (Firefox Windows desde 141). Provavelmente o caniuse marca o Firefox assim por o suporte não cobrir todas as plataformas. — [caniuse: WebGPU](https://caniuse.com/webgpu); contradito por [gpuweb wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- **(info antiga, nov/2025)** O web.dev anunciou "WebGPU is now supported in major browsers" (Safari 26, Firefox 141 Windows, Chrome). — [web.dev](https://web.dev/blog/webgpu-supported-major-browsers)
- **three.js**:
  - O manual descreve o `WebGPURenderer` como sucessor do `WebGLRenderer`, com fallback automático para backend WebGL 2 quando não há WebGPU. A opção `forceWebGL` testa esse caminho. — [three.js manual: WebGPURenderer](https://threejs.org/manual/en/webgpurenderer) (conteúdo obtido via resultado de busca; o fetch direto da página .html retornou 404, então trate como fonte parcial)
  - Releases de 2026 concentram esforço no WebGPURenderer e no TSL: WebXR no WebGPU (r185), MSAA XR (r186), `compileAsync` não bloqueante (r184), TSL 3x mais rápido para compilar (r184).
  - O WebGLRenderer segue recebendo features: SunLight com CSM e `compile()` com NodeMaterial (r186), camada de compatibilidade de NodeMaterial (r184).
  - — [three.js releases](https://github.com/mrdoob/three.js/releases)
- Blogs de terceiros de 2026 dizem que a migração é "quase uma linha" (exige init assíncrono). Relatam canvas preto silencioso em Firefox Linux. Consideram TSL o caminho recomendado para shaders custom (WGSL e GLSL a partir da mesma fonte). Essas fontes são de agências e opinativas. — [Utsubo: WebGPU + Three.js Migration Guide (2026)](https://www.utsubo.com/blog/webgpu-threejs-migration-guide); [buildmvpfast: WebGL to WebGPU migration 2026](https://www.buildmvpfast.com/blog/threejs-webgl-to-webgpu-renderer-migration-2026)
- **R3F**:
  - A v9.8.0 "gates" o setup assíncrono do WebGPURenderer.
  - A v10.0.0-alpha.6 torna o WebGPURenderer **default**, com fallback WebGL2, e GLSL passa a ser importado de `/legacy`.
  - — [R3F releases](https://github.com/pmndrs/react-three-fiber/releases)
- **Babylon**:
  - Suporta WebGPU desde a 5.0 (mai/2022). Os shaders do core foram reescritos em WGSL nativo em 2024. Uso: `new WebGPUEngine(canvas)` + `await engine.initAsync()`.
  - A doc diz que não há diferenças além da inicialização e que WebGL e WebGPU serão mantidos lado a lado "for the foreseeable future".
  - Não há troca automática de engine: é preciso escolher antes de criar a cena.
  - WebXR sobre WebGPU é experimental.
  - — [Babylon docs: WebGPU support](https://doc.babylonjs.com/setup/support/webGPU)
- O PlayCanvas se descreve como "built on WebGL2 and WebGPU". — [github.com/playcanvas/engine](https://github.com/playcanvas/engine)

### Inferences
- **[estimativa]** Um usuário do Takt em Firefox Linux ou Android, ou em Chromium Linux com GPU AMD ou Intel antiga, cai em WebGL2. Para um produto B2B em navegador corporativo (Chrome/Edge Windows), WebGPU estará disponível na maioria dos casos. O código precisa funcionar idêntico nos dois.
- **[estimativa]** Para cena low-poly flat-shaded com dezenas de draw calls, WebGL2 tem folga. O WebGPU só traria ganho real com compute shaders (ex.: simular milhares de peças na GPU), e isso não está no escopo, já que o log vem do backend.
- **[estimativa]** Recomendação de baixo risco para out/2026: começar com R3F v9 + `WebGLRenderer` (ou `WebGPURenderer` com `forceWebGL` em testes), sem shaders GLSL custom. Usar só materiais padrão (`MeshLambertMaterial`/`MeshStandardMaterial` com `flatShading`), o que torna a futura troca para WebGPU/R3F v10 praticamente transparente. Se for preciso shader custom, escrever em TSL.
- **[palpite]** O Firefox Linux deve ganhar WebGPU estável até o fim de 2026 ou início de 2027, conforme a intenção declarada da Mozilla. Não há data de versão.

### Gaps
- Não verifiquei nas release notes da Mozilla uma versão específica do Firefox Linux com WebGPU. Só existe a declaração "expects to ship in 2026".
- Não encontrei comparação oficial de paridade de features entre WebGPURenderer e WebGLRenderer no three.js (lista do que ainda não funciona no WebGPU).

## 4. Recursos de editor: grid snapping, picking, gizmos, outline, câmera, acessibilidade

### Takeaway
Nenhuma engine oferece um "build mode estilo The Sims" pronto. Grid snapping, rotação de 90° por tecla e validação de colisão são lógica de domínio do Takt em qualquer stack. Para o restante, as duas opções completas são o stack R3F + drei e o Babylon, que traz embutidos GizmoManager, SelectionOutlineLayer e até um pacote de acessibilidade. O R3F oferece:
- picking declarativo por eventos (com `instanceId`);
- TransformControls/PivotControls;
- OrbitControls/CameraControls;
- Outlines/postprocessing;
- Grid.

### Cited Findings
- **Raycasting e picking no three.js**: a interseção retorna `distance`, `point`, `face`, `faceIndex`, `object`, `uv`, `normal` e **`instanceId`** ("The index number of the instance where the ray intersects the InstancedMesh"). `raycaster.layers` filtra objetos testados. — [three.js docs: Raycaster](https://threejs.org/docs/pages/Raycaster.html)
- **Eventos R3F**:
  - Handlers `onPointerDown/Move/Click/...` são baseados em raycasting e entregues do mais próximo ao mais distante.
  - `stopPropagation()` também bloqueia objetos mais distantes. `onPointerMissed` no Canvas captura cliques no vazio.
  - Pointer capture serve para drag (`setPointerCapture`). `eventSource`/`eventPrefix` e `events.filter/compute` permitem customização.
  - Multi-pointer ainda não é suportado.
  - — [R3F: Events](https://r3f.docs.pmnd.rs/api/events)
- **TransformControls (addon do three.js)**: `setMode('translate'|'rotate'|'scale')`, `setSpace`, `translationSnap` (em unidades de mundo), **`rotationSnap` (em radianos)**, `scaleSnap`, `showX/Y/Z` e eventos `change`, `mouseDown`, `mouseUp`, `objectChange`. — [three.js docs: TransformControls](https://threejs.org/docs/pages/TransformControls.html)
- **drei `<TransformControls>`**: envolve um filho ou recebe `object`. Com `<OrbitControls makeDefault />`, os "Default-controls will temporarily be disabled automatically when the user is pulling on the transform gizmo". — [drei: TransformControls](https://drei.docs.pmnd.rs/gizmos/transform-controls)
- **drei `<PivotControls>`**: `activeAxes`, `disableAxes`, `disableSliders`, `disableRotations`, `disableScaling`, `autoTransform` e callbacks `onDragStart/onDrag(l, deltaL, w, deltaW)/onDragEnd`. Não há prop de snap: só `[tab]` para valores arredondados durante o drag. — [drei: PivotControls](https://drei.docs.pmnd.rs/gizmos/pivot-controls)
- **`camera-controls`** (base do `<CameraControls>` da drei): versão 3.1.2 (2025-11-17), ~2,7M downloads/semana. — [npm registry: camera-controls](https://registry.npmjs.org/camera-controls)

- **Babylon GizmoManager**:
  - Habilita gizmos de posição, rotação, escala e bounding box. `attachableMeshes` restringe alvos. `usePointerToAttachGizmos` faz o clique anexar automaticamente.

### Inferences
- **[estimativa]** O "build mode" ideal para o Takt **não usa gizmo de transformação livre**. Usa:
  1. raycast contra um plano do chão (ou o `point` do evento R3F);
  2. `Math.round(point / cellSize) * cellSize` para o ghost/preview;
  3. tecla `R` (ou botão) para rotacionar `+π/2`;
  4. validação de ocupação num grid lógico (Map de células) no store.
  - Isso é igual em qualquer engine. Os gizmos (TransformControls com `translationSnap=cellSize` e `rotationSnap=Math.PI/2`, só eixo Y via `showX/showZ=false`) servem como modo "avançado" opcional.
- **[estimativa]** A vista de cima pode usar a mesma cena com câmera ortográfica e controles travados (polar angle 0) ou alternância de `OrthographicCamera`. `CameraControls` (drei) faz transições animadas e é a opção mais robusta para alternar orbital e top view. **[palpite]** OrbitControls basta para o MVP.
- **[estimativa]** Para outline de seleção em R3F há três caminhos:
  - `<Outlines>` da drei: shell invertido por mesh, barato, mas não funciona por instância;
  - Outline do `@react-three/postprocessing`: pós-processamento por seleção;
  - **[palpite]** o mais simples, e coerente com o estilo flat: mudar a cor ou emissive da instância selecionada via `setColorAt` e desenhar um mesh "highlight" separado sobre o objeto selecionado.
- **[estimativa]** Acessibilidade de teclado num canvas 3D é responsabilidade da app em qualquer stack. O `@react-three/a11y` está parado desde 2022 e não declara suporte a R3F v9/React 19, então é risco usá-lo. O padrão mais sustentável é espelhar a cena num DOM acessível fora do canvas: lista ou árvore de elementos da linha, com foco, setas para mover no grid, R para rotacionar e Delete, sincronizada com o mesmo store Zustand. O `@babylonjs/accessibility` (HTML twin) é exatamente isso, mantido oficialmente, e é um diferencial do Babylon.
- **[estimativa]** Picking em InstancedMesh por `instanceId` resolve seleção de máquinas instanciadas. Para milhares de objetos, `three-mesh-bvh` acelera o raycast se ele virar gargalo (hover a cada pointermove).

### Gaps
- A página da drei sobre TransformControls não lista as props de snap. Que a drei repassa `translationSnap`/`rotationSnap` ao objeto three é dedução a partir da doc do three.js e não foi confirmado na doc da drei.
- Não consultei as páginas oficiais de `<Grid>`, `<Outlines>` e `<CameraControls>` da drei, nem o HighlightLayer/SelectionOutlineLayer na doc oficial do Babylon (só fórum e d.ts).
- Não encontrei solução "build mode" pronta (biblioteca de grid placement) madura para R3F ou Babylon.
- Não pesquisei o PlayCanvas a fundo quanto a gizmos fora do editor proprietário (há `pc.Gizmo` no engine 2.x, segundo conhecimento prévio não verificado nesta sessão). O README do `@playcanvas/react` não menciona gizmos.

## 5. Estratégias de teste para apps 3D em React

### Takeaway
Separe o domínio (grid, ocupação, snap, rotação, replay do log e cálculo de estado em T) em funções puras testadas com Vitest, sem WebGL nenhum. Esse é o maior ganho e não depende da engine. Use `@react-three/test-renderer` para asserções de scene graph e eventos sem browser. Use Playwright com SwiftShader (WebGL por software) para poucos testes E2E e visuais, verificando explicitamente qual renderer foi usado, porque WebGL em CI headless degrada de forma silenciosa.

### Cited Findings
- **`@react-three/test-renderer`**:
  - "React Three Test Renderer is testing library agnostic, so it works with libraries such as `jest`, `jasmine` etc."
  - Fluxo: `create(<Component/>)`, inspeção de `scene.children`/`allChildren` (que inclui geometria e material), `await fireEvent(mesh, 'click')`, `advanceFrames`.
  - — [R3F: Testing](https://r3f.docs.pmnd.rs/api/testing)
  - Versão `9.1.1` (2026-07-31), peer `@react-three/fiber >=9.0.0`, `react ^19`, ~40k downloads/semana. — [npm registry: @react-three/test-renderer](https://registry.npmjs.org/@react-three/test-renderer)
- **WebGL em CI headless** (via resultados de busca, fontes secundárias):
  - Em Chromium 139+, o fallback para SwiftShader passou a ser opt-in (`--enable-unsafe-swiftshader`).
  - Um conjunto de flags comum é `--use-gl=angle --use-angle=swiftshader-webgl --enable-unsafe-swiftshader`.
  - Se WebGL degradar sem GPU, o screenshot ainda "passa" com saída errada. Recomenda-se logar a string do renderer WebGL num teste de diagnóstico.
  - Há divergência entre rodar headless e headed sob xvfb.
  - — [microlink: WebGL without a GPU](https://microlink.io/blog/webgl-without-a-gpu); [chromedp: --enable-unsafe-swiftshader com --disable-gpu](https://chromium.googlesource.com/external/github.com/chromedp/chromedp/+/refs/tags/v0.14.1); [Chromium: headless osmesa → SwiftShader](https://chromium.googlesource.com/chromium/src.git/+/d99a9664c873fc38e226e33bc92da974fb852da3); [Dave Snider: GPU tests](https://backiee.wasmer.app/https_davesnider_com/posts/gputests)

### Inferences
- **[estimativa]** Pirâmide sugerida para o Takt:
  1. **Unit (Vitest, Node)**: lógica de layout (snap, colisão, rotação 90°, conectividade de esteiras), reducer do replay (estado em T a partir do log, seek, velocidade) e mapeamento estado→cor. Sem three.js ou com three.js só para matemática (`Vector3`/`Matrix4` rodam em Node sem WebGL).
  2. **Componente (`@react-three/test-renderer`)**: "clicar no elemento X seleciona no store", "N máquinas no store → InstancedMesh com count N", `advanceFrames` para verificar que o replay escreve matrizes.
  3. **E2E (Playwright + Chromium SwiftShader)**: fluxos de construção (colocar, rotacionar, apagar) com asserções via estado exposto (ex.: `window.__TAKT_STORE__` só em teste), e poucos snapshots visuais com tolerância (`maxDiffPixelRatio`), rodando sempre em `frameloop="demand"` ou com o relógio de simulação congelado para determinismo.
- **[estimativa]** Snapshots visuais WebGL variam entre GPU real e SwiftShader e entre versões de Chromium. Gere os baselines no próprio container de CI (imagem Docker oficial do Playwright) e nunca localmente.
- **[estimativa]** Testar WebGPU em CI headless é ainda mais frágil, o que reforça usar `forceWebGL`/WebGL2 em E2E.
- **[estimativa]** No Babylon existe `NullEngine` para rodar cena sem render em Node (conhecimento prévio, não verificado nesta sessão). Seria o equivalente ao test-renderer.

### Gaps
- Não verifiquei na doc oficial do Playwright as flags recomendadas para WebGL nem o comportamento padrão do `chromium-headless-shell` vs. Chromium "new headless" em 2026. As fontes acima são secundárias e divergem entre si.
- Não pesquisei Vitest Browser Mode (com Playwright provider) como alternativa para testes de componente com WebGL real.
- Não encontrei guia oficial de testes do Babylon nem do PlayCanvas.

## 6. Integração com React state stores (Zustand) e Next.js/Vite

### Takeaway
O R3F é um React renderer: a cena é JSX, compartilha contexto e hooks com a app e se integra naturalmente a Zustand, que é do mesmo coletivo pmndrs e tem padrão de leitura transitória documentado. Babylon e PlayCanvas são imperativos, e os wrappers React deles são pequenos (react-babylonjs ~1,7k/semana; @playcanvas/react 0.x, ~6k/semana). Vite funciona "out of the box". Next.js exige `transpilePackages: ['three']` e renderização só no cliente.

### Cited Findings
- **Zustand**: 5.0.15 (2026-08-13), ~37,7M downloads/semana, peer `react >=18`. — [npm registry: zustand](https://registry.npmjs.org/zustand)
- O R3F documenta o padrão transitório: ler `api.getState()` dentro de `useFrame` e atribuir ao ref, em vez de assinar reativamente valores que mudam rápido. — [R3F: Performance pitfalls](https://r3f.docs.pmnd.rs/advanced/pitfalls)
- O R3F 9.8.x suporta `<Activity>` e Strict Mode e descarta o renderer no unmount (9.8.1). A v10 alpha.6 declara suporte a React 19.3, StrictMode, Fast Refresh e `<Activity>`. — [R3F releases](https://github.com/pmndrs/react-three-fiber/releases)
- **Vite**: "vite will also work out of the box". **Next.js**: deve funcionar, mas add-ons não transpilados podem exigir configuração. Em Next 13.1+, adicione `three` em `transpilePackages`. O starter oficial é o `react-three-next`. A página não cobre App Router nem `'use client'`. — [R3F Installation](https://r3f.docs.pmnd.rs/getting-started/installation)
- **`react-babylonjs`**: 4.0.2 (2026-06-02), peer `@babylonjs/core >=8.32 <10`, `react >=19`. **`reactylon`**: 3.5.8 (2026-05-14), peer Babylon `^7||^8||^9`. — [npm: react-babylonjs](https://registry.npmjs.org/react-babylonjs); [npm: reactylon](https://registry.npmjs.org/reactylon)
- **`@playcanvas/react`**: "thin wrapper", com Suspense para assets, pointer events, física e ECS. O pacote `@playcanvas/blocks` traz componentes de alto nível. — [github.com/playcanvas/react](https://github.com/playcanvas/react)

### Inferences
- **[estimativa]** Arquitetura de estado recomendada para o Takt com R3F:
  - Um store Zustand de **layout** (elementos, posição de grid, rotação, seleção), lido reativamente por componentes, porque muda pouco: em eventos do usuário.
  - Um store ou ref separado de **playback** (tempo simulado, velocidade, cursor do log, estado derivado por elemento), lido **transitoriamente** em `useFrame` via `getState()`.
  - A UI 2D (painéis, timeline) assina o store com selectors e throttling (ex.: atualizar o relógio da UI a 10 Hz, não a 60 Hz).
- **[estimativa]** Com Babylon, o mesmo modelo exige uma camada de "binding" escrita à mão (subscribe do Zustand → mutar meshes), ou adotar `react-babylonjs`/`reactylon`, que têm base de usuários ~1.000–2.000x menor que o R3F. É mais código de cola e menos exemplos.
- **[estimativa]** Em Next.js App Router, o `<Canvas>` precisa estar num componente `'use client'` e, na prática, ser carregado com `next/dynamic` e `ssr: false` (padrão comunitário, não confirmado na doc oficial consultada). Para um editor que é SPA autenticada, Vite é a escolha mais simples. O SSR do Next não agrega nada à cena 3D.

### Gaps
- A doc oficial do R3F consultada não cobre App Router, `'use client'` nem `next/dynamic`. A recomendação acima vem de prática comunitária, não verificada nesta sessão.
- Não avaliei o `@playcanvas/react` em profundidade (estado de gizmos, picking, testes). O 0.x e a baixa adoção sugerem risco para um produto.
- **Síntese comparativa** (inferência consolidada, não é fato citado):
  - **R3F + drei**: melhor encaixe para app React + Zustand. Maior ecossistema, exemplos e contratáveis. Riscos: transição v9→v10 e manutenção irregular da drei.
  - **Three.js puro**: mesmas capacidades de render. Perde a integração declarativa com React, e o binding com o store fica todo à mão. Faz sentido só se a cena for isolada da UI.
  - **Babylon.js**: o mais "batteries-included" para editor (GizmoManager, SelectionOutlineLayer, Inspector, `@babylonjs/accessibility`, release semanal, backing da Microsoft). Integração React fraca.
  - **PlayCanvas**: engine forte e com usuários grandes, mas o valor dele está muito no editor proprietário. A integração React é imatura (0.x) e a adoção npm é a menor das quatro.
